# M41 — Cross-Domain Security Architecture Consolidation & Platform Freeze Review

Status: **Architecture governance review only. No prior milestone document modified. No code.**

Reviewed against: `m37-native-siem-architecture.md`, `m38-native-cloud-security-architecture.md`, `m39-native-vulnerability-engine-architecture.md`, `m40-native-ai-security-architecture.md` (cited below as M37/M38/M39/M40 with their own section numbers).

## 1. Cross-Domain Architecture Review

Read together, the four documents are **substantially coherent as one platform**, not four independent products — each explicitly builds on the prior milestones' precedents (Integration Hub discovery reuse, `IRiskContributionPort`, Evidence-referenced payloads, async pub/sub fan-out, computed/versioned graph artifacts, registry-driven pluggable content) rather than re-deriving them. That said, "each new document correctly cites the previous ones" is not the same as "the terminology and contracts are actually identical across all four," and this review's job is to find the gap between those two things. Nine concrete inconsistencies were found (§6); none require redesigning any milestone's bounded-context structure, and all are resolvable by amendment/convention rather than rework — which is the basis for this document's freeze recommendation (§9).

## 3. Canonical Ubiquitous Language

Resolving the specific terms the milestone instructed be reviewed, based on actual usage across all four documents:

- **Asset** — the canonical platform noun for anything discovered/inventoried, rooted in Integration Hub's `DiscoveredAsset`. Every domain-specific asset (`CloudResource`, `AISystemAsset`, a host/container/Kubernetes-node fingerprint target in M39) **must** be explicitly declared a specialization of `DiscoveredAsset`, following M38's precedent exactly. **Action required**: M40 must add this explicit statement for `AISystemAsset` (§6.5).
- **Resource** — used only as M38's cloud-domain-specific synonym for a cloud-provider-native asset (`CloudResource`); not a platform-wide synonym for `Asset`. No other milestone should introduce "Resource" as a competing generic term.
- **Identity** — the platform's existing Identity/RBAC bounded context's concept (a human or service principal with authentication/authorization state). Never used generically for "any identifier" — that concept is `EntityId`.
- **Principal** — a value used within `EntityRef`/permission-graph contexts (M38 `ciem`'s `PrivilegeFinding.principal_ref`) to mean "the identity/service-account performing or being evaluated for an action." Synonymous with `EntityRef` where `entity_type = identity`, not a separate concept.
- **Finding** — the canonical platform-wide noun for a human-triaged, lifecycle-managed security observation. **Canonical decision (§6.2)**: every domain-specific pipeline-output object (M37's `Alert`, M38's `CloudFinding`, M39's `VulnerabilityFinding`, M40's `AIFinding`) is a `[Domain]Finding` by convention going forward; M37's `Alert` is retroactively recognized as `SIEMFinding`'s established alias (see §6.2 for the exact resolution — not a rename, an explicit equivalence declaration).
- **Evidence** — exclusively the platform's existing Evidence bounded context; every domain's raw payload/proof is a *reference* into Evidence, never a duplicated store, consistent across all four documents already.
- **Alert** — retained as M37's domain-specific term for its `SIEMFinding` (see above); not used as a generic platform noun by any other milestone (M38/M39/M40 correctly did not use it).
- **Incident** — exclusively the platform's pre-existing `incident` bounded context (human/workflow construct that may aggregate multiple `[Domain]Finding`s across domains) — consistent across M37 §2.2/§8 and implicitly inherited by M38/M39/M40 findings' eventual same relationship (once §6.6's binding is resolved).
- **Risk** — exclusively Risk Engine Foundation's output. No domain computes or presents its own "risk score" as authoritative; all present a `PriorityScoreReference`/contribution-shaped value and label it as such (M38 §10/§13, M39 §7 explicit about this; M37 needs to be brought into this same discipline explicitly, §6.1).
- **Exposure** — M38's specific term (`cloud_exposure`, internet/identity/data/secrets/AI exposure aggregation). Not used generically elsewhere; consistent.
- **Threat** — used descriptively (M37 `siem_detection`'s behavioral/AI-assisted detections reference "threat correlation"; M38/M39/M40 reference the existing Attack Library for "threat-actor/TTP context") — never a distinct aggregate of its own in any document; consistent.
- **Policy** — used consistently as "tenant-configurable, versioned, registry-content" across `RetentionPolicy` (M37), CSPM policies (M38), guardrail policies (M40) — consistent pattern, different concrete policy types, no conflict.
- **Control** — used exclusively as `BenchmarkControl` (M38 §2.3, reused by M39 §10 and M40 §16) — consistent, single definition.
- **Compliance** — `cloud_compliance` (M38) as the canonical compliance-scorecard mechanism, explicitly reused by M39 §10 and M40 §16 rather than each building its own — consistent.
- **Attack Path** — exclusively M38's `AttackPathGraph`/Attack Path Engine (currently spike-pending per M38 §21.1); M39 explicitly consumes it rather than building a second one (§9 of M39); M40 does not introduce a competing concept — consistent, single owner.
- **Event** — every domain event across all four documents is a real, published, pub/sub-dispatched fact (never constructed-and-discarded, per the M37-established baseline) — consistent in *discipline*; **not** consistent in *naming convention* (§6.3).
- **Relationship** — Integration Hub's `RelationshipType` vocabulary (`DEPENDS_ON`, `OWNS`, `USES`, `AUTHENTICATES_WITH`, `CONNECTED_TO`, `PROTECTED_BY`, `MONITORED_BY`, `CONTAINS`, `RUNS`, `HOSTS`, `MEMBER_OF`) is explicitly reused verbatim by M38 §2.2. **M37, M39, and M40 reference Knowledge Graph relationships without explicitly re-confirming they use this same vocabulary rather than an ad hoc one** — a documentation gap, not necessarily a real divergence, flagged in §6.8.

## 4. Platform-Wide ADRs (governance decisions, this milestone)

**ADR-G1: `IRiskContributionPort` is the single, platform-wide risk-contribution contract for all security domains, retroactively including M37.**
Context: M38 introduced this port; M39 and M40 correctly reused it; M37 predates it and describes an ad hoc equivalent relationship instead.
Decision: M37's Risk Engine integration (§11 of M37: "`DetectionMatched`/`AlertRaised` are a genuine input signal *back* into Risk Engine's own scoring") is amended by reference (not by editing M37's document, per this milestone's constraint) to explicitly route through `IRiskContributionPort`, with SIEM-specific contribution fields (detection-confidence, correlation-severity, alert-frequency) as additive inputs, exactly matching how M39/M40 added their own domain-specific fields to the same port.
Consequence: exactly one risk-contribution contract exists platform-wide, with four current implementers (SIEM, Cloud Security, Vulnerability Engine, AI Security) and an explicit expectation that any future fifth domain (Identity Security, DSPM, etc., §8) extends this same port rather than proposing a new one.

**ADR-G2: `[Domain]Finding` is the canonical naming convention for every domain-specific pipeline-output/workflow aggregate; `Alert` is recognized as SIEM's historical name for this same concept and is not deprecated, but no future domain may introduce a new base term for this pattern.**
Context: §6.2. Renaming M37's `Alert` aggregate is out of scope for this governance-only milestone (would constitute modifying a prior milestone's architecture, explicitly forbidden); instead, this ADR fixes the *convention going forward* and records the equivalence.
Decision: `Alert` ≡ `SIEMFinding` for all cross-domain documentation, integration-contract, and platform-Findings-binding purposes (§5). Any future domain (Identity Security, DSPM, etc.) uses `[Domain]Finding`, never inventing a third base term.

**ADR-G3: Domain-Finding lifecycle-start events must use a single canonical verb, `[Domain]FindingOpened`, going forward; existing event names in M37–M40 are not renamed by this document but are recorded as the historical exception set requiring a compatibility mapping at implementation time.**
Context: §6.3 — `AlertRaised` / `CloudFindingOpened` / `VulnerabilityFindingDiscovered` / `AIFindingDiscovered` are four different verbs for the structurally identical "lifecycle begins" event.
Decision: `CloudFindingOpened`'s verb (`Opened`) is adopted as canonical, since it most precisely describes "a workflow lifecycle instance now exists," distinct from `Discovered` (which conflates the underlying detection event with the workflow-open event — a real semantic imprecision this ADR corrects going forward) and distinct from `Raised` (which is fine but less precise than `Opened` given `Alert`'s own later `AlertEscalated`/`AlertAcknowledged`/`AlertClosed` lifecycle already uses `Opened`-adjacent semantics implicitly). Any implementation work on M37–M40 should introduce `[Domain]FindingOpened` as the actual published event name, with the four documents' original terms understood as this governance document's translation table, not four independently-correct names.

**ADR-G4: `EntityRef` (defined in M37 §2.1) is the platform-wide typed-reference value object for any cross-aggregate pointer to an asset, identity, or AI system; every bounded context must use it rather than a bare `EntityId` or a parallel typed-reference concept.**
Context: §6.4 — M38 used it correctly; M39 used bare `EntityId`; M40 introduced `AISystemAssetRef` without clarifying its relationship to `EntityRef`.
Decision: `AISystemAssetRef` (M40) is declared an `EntityRef` specialization (`entity_type = ai_system`), not a parallel concept — a documentation clarification, not a redesign, since M40's own shared kernel already only needed a typed pointer, which is exactly what `EntityRef` already is. M39's bare `EntityId` references (`VulnerabilityOccurrence.asset_ref`, `Fingerprint.asset_ref`) are recorded as needing amendment to `EntityRef` at implementation time for consistency, though this is a low-severity fix (an `EntityId` is trivially wrappable in an `EntityRef` later without breaking M39's frozen shape, since `EntityRef.entity_id` already accommodates exactly this value).

**ADR-G5: `DiscoveredAsset` is the platform-wide asset root; every domain-specific asset concept must explicitly declare itself a specialization, including retroactively for pre-existing aggregates.**
Context: §6.5 — M38 did this correctly for `CloudResource`; M40 did not do this for the pre-existing `AISystemAsset`.
Decision: `AISystemAsset` is declared a `DiscoveredAsset` specialization for all future cross-domain integration purposes (asset search, exposure aggregation, risk contribution referencing). Since `AISystemAsset` predates Integration Hub Phase 2A/2B's discovery engine (confirmed in M40 §1 as a pre-existing aggregate), this may require a genuine implementation-time reconciliation (not merely a documentation fix) if `AISystemAsset`'s actual current shape does not already carry the fields `DiscoveredAsset` specialization requires (source connector, discovery provenance, fingerprint/identity) — this is exactly the kind of gap M40 §22's own "assumption 4" flagged as unverified, and this ADR formalizes it as a required verification, not an assumed-safe documentation note.

**ADR-G6: `RelationshipType` (Integration Hub's original enum, explicitly reused by M38) is the single platform-wide relationship vocabulary for every graph edge in every domain — SIEM investigation timelines, Cloud Security's resource/permission graphs, Vulnerability correlation contexts, and AI Security's agent-delegation/trust-boundary graphs all use the same enum, extended additively (never redefined) when a genuinely new relationship semantic is needed.**
Context: §6.8 — a documentation-completeness gap, not a confirmed divergence.
Decision: M37, M39, and M40 are recorded as needing an explicit confirmation statement (at implementation time, not by editing the frozen documents) that any graph edges they produce use this vocabulary; if a genuinely new relationship type is needed (e.g. M40's agent-delegation relationship, which does not cleanly map to any existing `RelationshipType` member), it is added additively to the one enum, never as a parallel domain-specific vocabulary.

## 5. Cross-Domain Contracts (consolidated, canonical)

1. **`IRiskContributionPort`** — one contract, four (soon five+) implementers (ADR-G1). Canonical shape: each domain publishes a domain-specific contribution record; Risk Engine Foundation composes them into the one authoritative risk score. No domain reads another domain's contribution directly — composition happens exclusively inside Risk Engine.
2. **`EntityRef`** — one contract, platform-wide (ADR-G4). Canonical shape: `{entity_type, entity_id: EntityId | None, raw_identifier: str}`.
3. **`[Domain]Finding` lifecycle** — one canonical state machine shape (`OPENED → VERIFIED* → ASSIGNED → (EXCEPTED | SUPPRESSED) → RESOLVED → REOPENED`, with domain-specific intermediate states as needed — e.g. M39's `VALIDATED` — permitted as additive extensions of this one shape, not a redesign per domain) (ADR-G2, ADR-G3).
4. **Evidence reference** — every domain's raw payload/proof is an `EvidenceRef`, never inline storage (consistent already, formalized here as a named cross-domain contract for completeness).
5. **`RelationshipType`** — one enum, additive-only extension (ADR-G6).
6. **`ConnectorPlugin`/`DiscoveryPage` (Integration Hub)** — one discovery/pagination contract, reused by `cloud_inventory` (M38), `vuln_detection` (M39), and `ai_discovery` (M40) without modification — already fully consistent across all three, the strongest existing cross-domain contract in the whole platform.
7. **Registry-driven pluggable content** — one pattern (additive registration, draft/active/deprecated lifecycle), independently instantiated per domain (normalizers, detection rules, CSPM policies, guardrails) but never re-architected — already consistent.

## 6. Duplicate Analysis (the nine concrete findings)

1. **M37 predates and does not use `IRiskContributionPort`** — resolved by ADR-G1. *Severity: Medium (documentation/consistency gap, not a functional duplicate).*
2. **`Alert` (M37) vs. `[Domain]Finding` (M38/M39/M40) — same structural pattern, different base name** — resolved by ADR-G2. *Severity: Low (cosmetic, but explicitly named because the milestone's own scope required reviewing "Alert" and "Finding" as distinct terms, and they are not, in fact, distinct concepts).*
3. **Four different lifecycle-start event verbs for the identical event** (`AlertRaised`/`CloudFindingOpened`/`VulnerabilityFindingDiscovered`/`AIFindingDiscovered`) — resolved by ADR-G3. *Severity: Medium — this is exactly the kind of naming drift that causes real integration bugs (a future cross-domain dashboard subscribing to "the finding-opened event" across all four domains has to know four different names instead of one).*
4. **`EntityRef` inconsistently adopted** (M38 correct, M39/M40 bypass it) — resolved by ADR-G4. *Severity: Medium — undermines the "one typed reference, platform-wide" goal M37 itself established.*
5. **`AISystemAsset`'s relationship to `DiscoveredAsset` left unstated** — resolved by ADR-G5, flagged as potentially requiring real implementation-time reconciliation, not just documentation. *Severity: High — this is the one finding in this review with a plausible path to an actual implementation-time surprise (a "specialization" that turns out not to structurally fit), not merely a naming inconsistency.*
6. **Domain-Finding → platform-Findings binding deferred four consecutive times** — not resolved by this document (this milestone is explicitly governance/consolidation, not new design), but formally escalated: **this is now a required design item for the next implementation-adjacent milestone, not a fifth deferrable placeholder.** *Severity: High (process risk — repeated deferral is itself the defect, independent of the binding's eventual design).*
7. **Cross-milestone SIEM-ingestion load risk raised three times, never closed** — same treatment as #6: formally escalated as a required pre-implementation validation, not a further-deferrable flag. *Severity: High (operational risk, not an architectural inconsistency, but repeatedly named without resolution is itself a governance failure this milestone exists to catch).*
8. **`RelationshipType` reuse confirmed for M38 only; unconfirmed (not necessarily wrong) for M37/M39/M40** — resolved by ADR-G6 as a required confirmation. *Severity: Low.*
9. **No genuine architectural/bounded-context duplication was found** across any of the four documents — worth stating explicitly as a positive finding, not merely the absence of a problem: none of M37/M38/M39/M40 independently reimplements discovery, event ingestion, graph storage, risk scoring, or evidence storage. Every one of the ~30 new bounded contexts across the four milestones was checked against the "reuse, don't rebuild" discipline and none violates it. *This is the review's most important finding, and it is a genuinely positive one.*

## 7. Required Refactoring (implementation-time, not this milestone)

None of the nine findings require any prior milestone's bounded-context structure, aggregate design, or event-flow architecture to be redesigned. Required work is exclusively: (a) documentation/convention amendments captured as this document's ADRs (G1–G6), to be applied as an implementation-time translation layer rather than edits to the frozen M37–M40 documents themselves, and (b) two genuine pre-implementation verification tasks — `AISystemAsset`'s structural compatibility with `DiscoveredAsset` specialization (finding #5), and the domain-Finding-to-platform-Findings binding design (finding #6), the latter of which is a **design task**, not a refactor, and should be scheped as its own small architecture spike before any of M37–M40 reach implementation, exactly as M39/M40 already each named their own domain-specific spikes.

## 8. Extension Strategy Validation

Reviewed against Identity Security, SOAR, Attack Path Engine (generalized beyond M38's cloud scope), Exposure Management (generalized beyond M38's cloud scope), DSPM, ASPM, SSPM, CNAPP, Network Detection, Executive Risk:

- **Identity Security**: fits cleanly as a sixth domain contributing to `IRiskContributionPort`, referencing the existing Identity/RBAC context the same way M38's `ciem`/M39's correlation/M40's agent-governance already do — no new cross-domain contract needed.
- **SOAR**: already uniformly named as a future consumer of `[Domain]FindingOpened`-equivalent events in M37 §11, M38 §11, M39 §11 — consistent placeholder across all three, no new work needed to accommodate it structurally once ADR-G3's canonical event name lands.
- **Attack Path Engine (generalized)**: M39 §11 already explicitly designed `vuln_prioritization`/`vuln_correlation` to consume "whichever attack-path capability exists... without needing rework if/when it generalizes" — this is confirmed forward-compatible by construction, a genuine example of one milestone correctly anticipating another's evolution.
- **Exposure Management (generalized)**: M38's `cloud_exposure` is scoped cloud-specific; a platform-wide Exposure Management capability would need to become a tenth-ish cross-domain aggregation context consuming `cloud_exposure`, AI Security's implicit exposure signals (M40 §5's AISPM), and Vulnerability Engine's KEV/internet-facing exposure — architecturally straightforward (same aggregation-read-model shape as every `*_exposure`/`*_analytics` context already in this platform) but not yet designed as its own context; recorded as a clean future extension, not a gap.
- **DSPM/ASPM/SSPM**: each fits the established pattern (a domain-specific posture-management context following M38 CSPM's registry-policy shape, contributing to `IRiskContributionPort`, referencing `DiscoveredAsset`-specialized assets) — no platform-level contract changes anticipated.
- **CNAPP**: RedForge's M38 already **is** a native CNAPP by this platform's own explicit framing (§0 of M38) — no additional extension design needed, this is already delivered architecture, not a future one.
- **Network Detection**: fits as either a SIEM (M37) source category or a Cloud Security network-topology signal (M38 §4) depending on scope — no new cross-domain contract needed, existing `EventSource`/CEM extensibility (M37 §2.1/§2.3) already accommodates it.
- **Executive Risk**: a read-model/dashboard composition over `IRiskContributionPort`'s aggregate output across all current and future domains — already the correct shape given ADR-G1's consolidation, no new contract needed.

**No extension-strategy gap was found** that would require a new cross-domain contract beyond the six already consolidated in §5.

## 9. Architecture Governance Recommendations

1. Adopt ADR-G1 through ADR-G6 as binding platform-wide conventions for all implementation work proceeding from M37–M40, applied as a translation/amendment layer rather than edits to the frozen documents (per this milestone's explicit constraint).
2. Schedule the domain-Finding-to-platform-Findings binding (finding #6) as its own named architecture spike before any of M37–M40 begins implementation — do not allow a fifth milestone to defer it again.
3. Schedule the SIEM shared-ingestion load validation (finding #7) as a required operational pre-implementation task, tracked jointly across whichever of M37–M40 implements first.
4. Verify `AISystemAsset`'s actual structural compatibility with `DiscoveredAsset` specialization (finding #5) before M40 implementation begins — this is the one finding in this review with genuine risk of an implementation-time surprise.
5. No prior milestone's document should be edited to satisfy this review — all six ADRs are additive governance decisions layered on top, consistent with this milestone's explicit constraint not to modify existing architecture documents.
6. Future domains (Identity Security, DSPM, ASPM, SSPM, generalized Exposure Management) should be held to the six cross-domain contracts in §5 from their first architecture-milestone draft, rather than each independently rediscovering them the way M37→M38→M39→M40 each incrementally converged on them.

## 10. Platform Freeze Recommendation

# PLATFORM ARCHITECTURE FROZEN WITH REQUIRED CONSOLIDATION

**Evidence-based justification**: the four native security-domain architectures are overwhelmingly coherent as one platform — zero genuine bounded-context or capability duplication was found (finding #9), and the dominant pattern across all nine findings is *convergent* design (each milestone correctly reusing the prior ones' proven mechanisms) with a small number of *terminology and contract-naming* gaps left behind by that same incremental convergence process. None of the nine findings require redesigning any milestone's domain model, aggregates, or event flow. Two findings (the Finding-to-Findings binding, and the SIEM ingestion-volume risk) are process failures — the same open question named repeatedly across milestones without resolution — and must be closed before implementation, not architecturally reworked. One finding (`AISystemAsset`/`DiscoveredAsset` compatibility) carries genuine implementation risk and requires verification, not redesign. The remaining six findings are resolved in full by this document's six ADRs, applied as an additive consolidation layer.

This is not a clean, zero-issue freeze — hence "with required consolidation," not an unconditional freeze — but it is also not a deferral: nothing found here casts doubt on the platform's fundamental architectural coherence, and every required action is scoped, named, and assigned to a specific pre-implementation step rather than left open-ended.
