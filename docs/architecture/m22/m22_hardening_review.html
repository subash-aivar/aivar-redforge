PART 1

Architecture Stress Review

Threat Intelligence Domain

P0Dual graph model — in-memory KnowledgeGraph vs. PostgreSQL security_graph are not reconciled
The architecture draft references wiring threat intel nodes into "the security graph." The repository contains two distinct graph implementations: (a) the production-grade domain/security_graph/ontology.py backed by PostgreSQL with strict ontology enforcement (ONTOLOGY_VERSION=6, closed NodeKind/EdgeKind enums, pair-validation in validate_edge()); and (b) an in-memory KnowledgeGraph application service with its own node/edge model that explicitly acknowledges "state is lost on process restart." The draft does not state which graph is the integration target. If M22 projects threat intel nodes into the in-memory graph, they will disappear on restart. If M22 extends the PostgreSQL ontology, it must define new NodeKind and EdgeKind values, which requires bumping ONTOLOGY_VERSION and updating all callers of validate_edge(). This ambiguity must be resolved before any implementation begins.
  • Decision required: M22 threat intel nodes go into the PostgreSQL-backed security graph (ontology v7), not the in-memory KnowledgeGraph.
  • Required: Define exactly which new NodeKind values are needed (e.g. ATTACK_TECHNIQUE, THREAT_ACTOR, VULNERABILITY) and which new EdgeKind values (e.g. USES_TECHNIQUE, EXPLOITS_VULNERABILITY, ATTRIBUTED_TO, PRECEDES) before implementation, with valid pair constraints.
P1SourceDomain enum is not extensible — THREAT_INTEL source registration has no clear path
The M21 correlation engine uses SourceDomain from domain/investigations/value_objects.py as a closed StrEnum. The architecture proposes registering threat intel as a correlation source via a ThreatIntelInvestigationAdapter. Adding SourceDomain.THREAT_INTEL to the enum is a domain model change that also touches RULE_VERSIONS, evaluate_pair()'s source-domain logic, and the source_adapters.py module. This is manageable but must be planned explicitly — it is not just "add an adapter."
P1STIX ingestion has no size or schema validation gate defined
The architecture permits ingesting STIX 2.1 bundles via file upload or TAXII pull. A STIX bundle from a misconfigured or malicious source can be arbitrarily large (MITRE ATT&CK Enterprise STIX bundle alone is ~15MB; third-party feeds can be hundreds of MB). No maximum bundle size, no object-count cap, and no schema validation strategy (beyond "the stix2 library handles it") are defined. The stix2 library validates schema but does not bound memory usage during parsing of maliciously crafted deeply-nested bundles.
P2TAXII pull frequency is "admin-configurable" with no floor or circuit breaker defined
An admin who sets a TAXII pull interval to 30 seconds against an external endpoint could generate egress throttling, get the RedForge instance blocked, or exhaust the database with duplicate ingestion attempts. The architecture must define a minimum poll interval floor (e.g. 1 hour) and a back-off policy when the TAXII endpoint is unavailable.
P2No idempotency key defined for STIX object upsert across multi-tenant orgs
ATT&CK techniques are global (not per-tenant). The proposed stix_ingestion_log with a unique index on (org, source, stix_id) implies per-org tracking, but ATT&CK technique rows are global — they must NOT be per-org. The architecture conflates two different idempotency contracts: (a) global static data (ATT&CK techniques, CVEs, KEV list) which is seeded once and upserted on sync, and (b) org-scoped STIX bundles (from TAXII or upload) which are per-tenant. These require different idempotency strategies and must not use the same table.

Threat Fusion Engine

P0AggregatedRisk VO semantics are undefined — what happens when all providers fail?
The fusion layer must produce an AggregatedRisk for each indicator. If all configured providers return failures (rate-limited, auth failure, timeout), the aggregate has no constituent evidence. The architecture does not define whether AggregatedRisk in this state is: (a) absent (no record produced), (b) a sentinel "no data" state, or (c) inherits the cached stale values. If (c), stale evidence from an expired enrichment could be used as current investigation evidence — a correctness defect.
P1FusionConflictPolicy weight table has no defined default — new tenants will have undefined behavior
Source weights are "admin-configurable per org" in a proposed threat_intel_fusion_config table. What happens for a new tenant with no weight configuration? If weights default to 1.0 for all providers, a provider with a history of false positives (e.g. aggressive AbuseIPDB scoring) gets equal trust as a high-fidelity source. The default weight table must be defined and documented before implementation.

Attack Path Engine

P0PathExplosionPolicy caps are hardcoded in the architecture but not tested against real graph density
The architecture specifies "max depth 12, max fan-out 8." These numbers are asserted without validation against the actual PostgreSQL-backed security graph schema. The existing graph stores edges in the knowledge_graph_edges table (or equivalent). At depth 12 with fan-out 8 in a large graph, the worst case is 8^12 = 68 billion potential paths before pruning. Even with aggressive pruning, this traversal against a PostgreSQL table with millions of edge rows will produce timeouts at realistic tenant scale. The depth cap should be validated with explain-analyze queries on representative data before being committed to the domain model.
P1Attack path seed entity selection is undefined — who triggers computation and when?
The architecture describes BFS "from a seed entity (typically an IP flagged as an IOC, or an entity involved in a behavioral detection)" but does not define: (a) when path computation is triggered (on investigation open? on IOC match? on schedule?); (b) who selects the seed entity from potentially many IOC-flagged IPs in a large investigation; (c) whether paths are computed proactively for all active investigations or only on demand. Without this, P5 implementers have no contract to build against.
P1PathStatus lifecycle is undefined
The AttackPath aggregate has a status: PathStatus field with values ACTIVE | CONTAINED | HISTORICAL but no transition rules are defined. Who transitions a path from ACTIVE to CONTAINED? What evidence triggers HISTORICAL? Without a state machine, the status is meaningless metadata.
P2InferenceGatePolicy's "adjacent observed step" requirement is ambiguous
The policy states "an inferred step is allowed only if at least one adjacent step is OBSERVED." "Adjacent" means the immediately preceding or following step in the path sequence. However, if the BFS visits non-sequential hops (as is common in real attack paths where lateral movement skips intermediate nodes), the adjacency requirement might be satisfied by a step that is structurally adjacent in the array but not actually causally related. The policy needs a precise definition: "adjacent" means step sequence number ±1, not graph-distance.

Background Workers

P1Worker pattern assumes single-process deployment — no distributed lock for global sync workers
The existing BehaviorDetectionWorker uses a PostgreSQL advisory lock (pg_try_advisory_xact_lock) with a hardcoded hash (0x42424242BEEF0001) to prevent duplicate processing. The M22 global sync workers (AttackTechniqueSyncWorker, VulnerabilitySyncWorker) operate on global data, not per-org data, so the existing per-org lock pattern does not apply. These workers need their own advisory lock hashes that are globally unique and documented. If two horizontally-scaled instances both run the sync worker simultaneously, one will overwrite ATT&CK technique rows with identical data (idempotent via upsert) but may cause unnecessary load on NVD API and hit rate limits.
P2MAX_ORGS_PER_CYCLE = 50 cap in existing workers creates a fairness starvation problem at scale
The existing detection workers cap at 50 orgs per cycle. IndicatorRefreshWorker will process active investigations' indicators. At 1,000 tenants, the bottom 950 orgs get no indicator refresh in the current cycle. This is acceptable for detection workers (5-minute windows) but unacceptable for active investigation enrichment where SLA expectations are higher. The refresh worker needs a priority-queue model based on investigation recency, not a simple org-list head.

API Layer

P1Attack path compute endpoint has no timeout, quota, or cost throttle
POST /attack-paths/compute triggers a BFS traversal over the security graph. This is an expensive operation. The architecture does not define: per-tenant rate limits, maximum concurrency, request timeout, or cost accounting. A single API call could trigger a multi-second graph traversal that blocks the async event loop or consumes significant DB connection time.
P2ATT&CK Navigator JSON export — no size cap or pagination defined
An ATT&CK Navigator layer JSON export for a tenant with all 700+ techniques mapped could be a multi-MB synchronous response. No streaming, no background job, no size limit is defined.

Frontend Architecture

P2Attack path visualization strategy not defined — graph rendering at depth 12 is non-trivial
A path with 12 steps and branching is a directed acyclic graph, not a simple list. The architecture assumes a Next.js page but does not specify: (a) whether the visualization is a static timeline, a force-directed graph, or a swimlane diagram; (b) what library is used (D3, React Flow, Cytoscape.js all have different bundle size and CSP implications); (c) how to handle paths with more than 20 nodes without overwhelming the user. This is a UX architecture gap, not just a styling choice.
PART 2

DDD Validation

Aggregate Boundary Violations

P0AttackPath aggregate contains a list[AttackStep] — this is an unbounded collection anti-pattern
The proposed AttackPath aggregate holds steps: list[AttackStep] directly on the aggregate root. In DDD, aggregates should have small, bounded collections. An attack path at max depth 12 with branching could contain dozens of steps, each with an evidence_ids: list[str]. Loading the entire aggregate for every query — including simple status checks — loads all steps and all evidence references. The correct pattern (following the existing InvestigationCase design) is: the aggregate root holds summary state (step count, technique coverage, confidence) and steps are a separate, lazily-loaded collection fetched via a dedicated repository query. The draft violates this pattern.
P1AttackTechniqueNode is named as an "aggregate" but is a read-only reference data object
ATT&CK technique records are globally seeded, never mutated by business logic, and have no lifecycle or invariants to protect. Calling them aggregates is incorrect DDD. They are reference data — effectively a read-only projection of an external standard. The correct modeling is: an AttackTechnique entity (not aggregate) loaded via a dedicated AttackTechniqueRepository that is read-only. Elevating them to aggregate status imposes unnecessary overhead (version columns, optimistic concurrency) on data that never changes concurrently.
P1VulnerabilityRecord has the same reference-data problem as AttackTechniqueNode
CVE records are externally owned, globally seeded, and updated only by the sync worker. They are not tenant-owned business objects. Modeling them as aggregates implies they can be created, modified, and versioned by business logic — none of which is true. They are reference data entities.
P1ThreatActorProfile — the boundary between global and tenant-scoped actor data is undefined
Some threat actor data is globally sourced (from MITRE ATT&CK groups, from an organization's TAXII subscription), while some is tenant-specific (a tenant's own analyst attribution notes). The architecture does not define this boundary. A global ThreatActorProfile is reference data. A tenant's attribution of a specific incident to that actor is a relationship, not a modification of the actor profile. Mixing these two concerns in one aggregate will cause cross-tenant data leakage if not carefully partitioned.

Value Object Issues

P2FusionWeight is a VO on the aggregate but represents configuration — it belongs in a policy, not data
FusionWeight (per-source trust weight) is described as a VO on the fusion config. In practice it is a policy parameter read from a config table. Encoding it as a VO inside the aggregated risk implies it travels with every indicator — which bloats every fusion result with weight metadata. The weight should remain in the FusionConflictPolicy, not in the AggregatedRisk VO. The AggregatedRisk VO should record the weights that were applied as audit-trail metadata, but not own the weight configuration.
P2PathConfidence is described as "weakest link" — this needs explicit domain modeling
PathConfidence deriving from the weakest step is a good rule, but it reuses CorrelationConfidence from M21. There is a semantic risk: M21's CorrelationConfidence was designed for investigation evidence correlation; applying it to attack path steps conflates two different confidence domains. A path step's confidence is about the quality of evidence for that specific step; an investigation's confidence is about the strength of cross-domain correlation. They may happen to use the same four-level enum now, but future calibration of one should not automatically recalibrate the other. Even if the enum values are identical, they should be separate types.

Repository Boundaries

P1AttackPathRepository query "by root technique" crosses aggregate boundaries
The proposed AttackPathRepository.find_by_root_technique(technique_id) query implies a join from attack_paths to attack_path_steps to attack_techniques. This is a cross-aggregate query implemented in a repository — which is correct — but the result set can be enormous in a large tenant (many paths share the same root technique). This query needs a mandatory tenant-scoped filter and a pagination contract at the repository interface level, not left to the caller.

Domain Events

P1No domain events defined for M22 — the entire bounded context is event-silent
The existing M21 InvestigationCase produces domain events (InvestigationCaseOpened, EvidenceAttached, SeverityEscalated, etc.) that drive projections, audit, and downstream subscribers. The M22 draft defines zero domain events. At minimum the following should be defined: AttackPathComputed, AttackPathUpdated, ThreatActorAttributed, TechniqueSyncCompleted, IndicatorFused. Without events, downstream integration (e.g. investigation update on new path, SSE notifications, audit log) requires synchronous coupling instead of event-driven decoupling.

CQRS Boundaries

P2Attack path computation straddles the command/query boundary — no CQRS split defined
AttackPathService.compute() is both a command (it writes a new AttackPath to the database) and a query (it reads the security graph, reads enrichments, reads techniques). Without an explicit CQRS boundary, this service will accumulate read-side logic that makes testing the write side difficult. The compute operation should be: (a) a command that schedules or triggers path computation; (b) a separate query service that reads the precomputed path. This matches the existing IndicatorQueryService / IndicatorEnrichmentService split already established in M18.

Anti-Corruption Layer

P1No ACL defined between STIX object model and RedForge domain model
The StixIngestionService will parse STIX 2.1 objects (using the stix2 Python library) and map them to domain objects (ThreatActorProfile, AttackTechniqueNode, etc.). This mapping is an anti-corruption layer and must be explicitly defined. The architecture refers to "maps to domain objects" without specifying how STIX relationships, confidence scores (which are 0–100 in STIX), and STIX object versioning (modified, spec_version) are translated into RedForge's four-level confidence enum and domain model. A STIXToDomain translator class must be defined with explicit field mappings before implementation.

Shared Kernel

P2EvidenceCandidate / NormalizedEntity reuse from M21 may create inappropriate coupling
The threat intel investigation adapter will produce EvidenceCandidate objects (from M21's domain). This creates a direct dependency from the threat_intel bounded context to the investigations bounded context. In strict DDD, bounded contexts should not import each other's domain objects. The adapter should operate at the application layer and use an explicitly defined shared kernel or ACL — not import domain value objects across context boundaries.
PART 3

Database Review

Table Design Issues

P0Global reference tables (attack_techniques, vulnerabilities) must NOT carry organization_id
ATT&CK techniques and CVE records are global. If these tables carry an organization_id column (following the pattern of every other table in the codebase), the sync worker will need to insert a separate row per tenant for every technique and CVE, scaling storage O(tenants × techniques × CVEs). At 1,000 tenants × 700 techniques × 200,000 CVEs = 140 billion rows. This is architecturally catastrophic. These must be true global tables with no organization_id. The association between a tenant and their relevant techniques is a separate join table (org_technique_observations or similar), not duplication of the reference data.
P0attack_path_steps as a child table needs a migration-time ordering clarification
The draft puts attack_path_steps in migration 0038 alongside attack_paths. However, if attack_path_steps.attack_path_id FKs to attack_paths.id, both must be in the same migration (or attack_paths must precede). This is correct as stated, but the migration must also define: (a) whether sequence is enforced unique per path at the DB level (partial unique index on (attack_path_id, sequence)); (b) whether the evidence_ids column is a PostgreSQL array or a separate attack_path_step_evidence join table. An array of FK-like strings is not referentially integrity-enforced — a join table is safer.
P1stix_ingestion_log — the (org, source, stix_id) unique index conflates global and tenant data
If ATT&CK STIX objects are global (no org_id), the ingestion log's unique key cannot include org_id for global objects. But for tenant-specific TAXII bundles, org_id IS required. The log needs two distinct unique constraints: (source_type='global', stix_id) for global syncs and (org_id, source_type='taxii', stix_id) for tenant TAXII. A single unique constraint cannot serve both.
P1No partitioning strategy for threat_intel_enrichments growth
The existing threat_intel_enrichments table (migration 0029) will grow continuously as M22 adds more indicator types and auto-enrichment. At 1,000 tenants × 10,000 indicators per tenant × 8 providers = 80 million enrichment rows. An index on (organization_id, last_seen_at) helps for single-tenant queries but a full-table TTL cleanup scan becomes expensive. Consider range partitioning by expires_at month to allow partition-drop for expired data instead of row-level DELETE.

Index Strategy

P1attack_techniques full-text search requires a GIN index — not mentioned in the architecture
The architecture specifies AttackTechniqueRepository.search_by_name(query). A LIKE or ILIKE query on name without an index performs a full table scan. With 700+ techniques today and growth from CAPEC/ATT&CK for ICS/ATT&CK for Mobile, a GIN index on a tsvector column is required. This must be in the migration definition.
P2Composite index order matters for fusion query pattern — not specified
The primary query pattern for the fusion layer is: "for this org, fetch all enrichments for this indicator that are not yet expired, ordered by provider." The index must be (organization_id, indicator_id, expires_at DESC) — not just (organization_id, indicator_id) — to support the TTL filter efficiently. The existing 0029 migration's indexes may need extension.

Migration Safety

P1Four migrations (0035–0038) are planned but only one was budgeted for global sync tables
Migrations 0035 (ATT&CK + CVE), 0036 (threat actors + TAXII), 0037 (fusion config), 0038 (attack paths) are proposed. The initial bulk load of ATT&CK techniques in migration 0035 — if it includes INSERT statements — will make the migration non-transactional if the insert count is large. Alembic's migration runner wraps DDL in transactions, but bulk data inserts should be deferred to the application sync worker, not embedded in the migration. Migration 0035 should only create the schema; data is seeded by the sync worker on first startup.
P2Rollback from 0035 will leave orphaned global data if the sync worker has run
If migration 0035 is applied and the ATT&CK sync worker runs, then migration 0035 is rolled back, the tables are dropped but the sync worker's external state (advisory lock hash, last-sync timestamp) may still be in the system. The down_revision function in the migration must also account for cleaning up any data that the sync worker may have written. Since sync worker state is not in the migration schema, this is an operational risk that must be documented.

Deadlock Analysis

P1Attack path computation + enrichment refresh on the same indicator can deadlock
If AttackPathService reads enrichments for an indicator (shared lock) while IndicatorRefreshWorker upserts new enrichments for the same indicator (exclusive lock) within the same transaction, a lock ordering issue can occur if these operations span two sessions with different lock acquisition order. The existing enrichment upsert pattern uses INSERT ... ON CONFLICT, which PostgreSQL handles atomically, but the attack path service's transaction may hold a read lock on the same row. Define lock ordering explicitly.
PART 4

Security Review

SSRF

P0TAXII endpoint URL is admin-configurable — classic SSRF vector
The architecture allows per-org admins to configure a TAXII 2.1 endpoint URL. If this URL is not validated, a malicious or compromised admin can set the TAXII URL to an internal network resource (e.g. http://169.254.169.254/latest/meta-data/ for AWS metadata, or http://internal-postgres:5432). RedForge will then fetch that URL using the server's outbound HTTP client. This is a textbook SSRF vulnerability. Mitigations required before implementation: (a) URL scheme restriction to https:// only; (b) DNS resolution of the hostname must not resolve to RFC-1918, link-local, or loopback addresses; (c) TAXII fetch must use a dedicated HTTP client with explicit no-redirect policy.

STIX Parsing Risks

P0Malicious STIX bundle can trigger object graph explosion during parsing
The stix2 Python library resolves STIX relationships by building an in-memory object graph. A crafted STIX bundle with thousands of self-referential or circular relationship objects can cause memory exhaustion during Bundle.parse(). Before calling any stix2 parse function, the raw JSON must be pre-validated for: (a) object count cap; (b) relationship count cap; (c) nesting depth cap. The pre-validation must happen at the raw bytes / JSON level, before the stix2 library is invoked.
P1STIX external references contain arbitrary URLs — secondary SSRF via reference resolution
STIX 2.1 objects carry external_references with url fields. If the ingestion service ever attempts to resolve these URLs (for context enrichment or validation), this creates a secondary SSRF vector from STIX bundle content. The architecture must explicitly state that external reference URLs from STIX bundles are stored as text metadata and never resolved by the server.

Tenant Isolation

P0Global tables (attack_techniques, vulnerabilities) must have a read-only RBAC policy that prevents tenant modification
If attack_techniques and vulnerabilities are global tables, any SQL injection in the application layer that bypasses the application's read-only access pattern can allow a tenant to modify global reference data — corrupting ATT&CK technique records for all tenants. The application service layer must use a read-only database role (or schema permission) for all queries against global tables. Only the sync worker (running under a privileged role) may write to these tables.
P1Cross-tenant attack path construction via shared global technique nodes
If AttackPathService traverses from an entity to an ATTACK_TECHNIQUE node (global), then to another entity via that technique, it could potentially traverse into another tenant's graph if the join condition does not enforce organization_id on every hop through entity nodes. Every graph traversal hop that passes through a global node (technique, CVE) must re-assert the tenant filter on the next hop's entity side.

Credential Storage

Credential handling — existing pattern is sound
The existing credential_ref pattern (an env-var name, never a secret value) is the correct approach. M22 must extend it for any new providers (NVD API key, TAXII auth tokens) using exactly this pattern. The CredentialResolutionError exception ensures the actual credential value never appears in exception messages. This is correctly designed and must be preserved.

API Abuse

P1STIX bundle file upload needs a hard byte-size limit enforced at the HTTP layer, not the application layer
The architecture describes STIX bundle upload without specifying where the size limit is enforced. Application-layer size checks happen after the web framework has already buffered the request body — a 500MB upload still reaches memory. The limit must be configured at the FastAPI/uvicorn/nginx layer (max_request_body_size) before the route handler is invoked.
P2Attack path compute can be abused as a resource-exhaustion vector by authenticated tenants
Any authenticated user with SECURITY_OPERATIONS_READ permission could submit many POST /attack-paths/compute requests concurrently, triggering parallel BFS traversals. A per-tenant concurrency limit and per-tenant daily compute-budget (number of paths computed per day) must be defined and enforced.

Graph Traversal Abuse

P1PathExplosionPolicy is enforced in application code — a bypassed policy allows unbounded DB queries
PathExplosionPolicy caps depth and fan-out in application code. But the underlying PostgreSQL recursive CTE (if used for graph traversal) does not have this cap at the DB layer. A bug in policy enforcement allows a single query to generate millions of intermediate rows. The PostgreSQL query itself should have a LIMIT or a RECURSIVE ... CYCLE clause as a defense-in-depth cap, independent of application-level enforcement.

Hot Paths

  • Enrichment cache lookup — every investigation correlation check hits threat_intel_enrichments for each involved IP. Must be a single indexed read, not a multi-join query.
  • STIX ingestion parse — synchronous during file upload; must be moved to a background task for bundles >1MB.
  • Attack path BFS — must never run in the API request path for large graphs. Must always be a background task with a job ID returned immediately.

Memory Pressure

  • STIX bundle parsing via stix2 library builds an in-memory object graph. A 50MB bundle can consume >500MB of memory during parsing due to Python object overhead. The uvicorn worker process will OOM if multiple concurrent uploads are not throttled.
  • ATT&CK STIX bundle (Enterprise) is currently ~15MB JSON, yielding ~200MB in-memory during parse. This is safe for a single worker process but unsafe if concurrent.

P1Missing: False positive feedback loop — this is a critical enterprise usability requirement
Every major enterprise TI platform allows analysts to mark an IOC as a false positive, which (a) suppresses future alerts for that indicator, (b) optionally feeds back to provider scoring, and (c) is tracked in the audit log. Without this, RedForge will generate alert fatigue as benign IPs in shared hosting environments (CDNs, Cloudflare, AWS ranges) accumulate AbuseIPDB reports and continuously appear as threats. This should be designed in M22 even if deferred to M23 for full implementation.
P1Missing: CVE-to-asset linkage — CVE without affected asset context has limited operational value
Storing CVE records is a prerequisite. But the enterprise value is knowing which of your assets are affected by which CVEs. The architecture does not define how CVEs are linked to the existing asset/inventory bounded context. A CVE record in isolation is a reference database entry; a CVE linked to a specific AIAsset or AITarget is actionable intelligence. M22 should at minimum define the data model for this linkage, even if the full asset-scan integration is deferred.

  • SourceDomain enum extension requires domain model surgery

  • AttackTechniqueNode and VulnerabilityRecord misclassified as aggregates (should be reference entities)
  • No ACL defined for STIX-to-domain translation

Architecture Strengths

What is genuinely well-designed
  • Closed ProviderName StrEnum — no free-text provider strings anywhere is a correct and disciplined pattern that prevents a whole class of bugs and injection risks.
  • Evidence-first attack path design — the hard invariant "no fabricated steps" with the InferenceGatePolicy is architecturally correct and avoids the AI hallucination problem common in threat intelligence tools that use LLM-generated attack narratives.
  • CorrelationConfidence enum reuse from M21 — a four-level explainable enum (not a mysterious 0–100 score) is the right design for a security product. The principle is sound even if the specific reuse is a semantic coupling risk.
  • Existing PostgreSQL threat_intel foundation (M18) — migration 0029 established the right patterns: per-org provider config, TTL caching, provider health tracking, and tenant isolation via FK. M22 builds on solid ground.
  • Credential resolution via env-var reference — the pattern of storing a reference name (never the secret value) and resolving at runtime is correct. The CredentialResolutionError is correctly designed to never expose the credential value.
  • TAXII as consumer only (not hosting) — correct scoping. Being a TAXII server adds significant compliance and operational surface area that M22 does not need.
  • BFS over PostgreSQL (not a graph DB dependency) — avoids introducing Neo4j/Neptune as an infrastructure dependency at this scale. The known scaling boundary at 10B edges is correctly acknowledged as a future decision.
  • Phase ordering: static data first (P1) — starting with ATT&CK and CVE before any live API integration is correct; it enables testing without provider keys and reduces implementation risk.

Required Changes Before Implementation

  1. Decide and document: global vs. tenant table architecture for attack_techniques, vulnerabilities, and stix_ingestion_log. This is the most consequential structural decision in M22.
  2. Resolve the dual graph model: explicitly document that M22 targets the PostgreSQL-backed security_graph (not the in-memory KnowledgeGraph) and define the new NodeKind/EdgeKind values for ontology v7.
  3. Run BFS performance proof-of-concept on the current security graph tables before committing to the depth-12/fan-out-8 caps. Adjust based on EXPLAIN ANALYZE results.
  4. Define the STIX ACL translator interface — field-by-field mapping from stix2 Python objects to RedForge domain VOs, including confidence translation and versioning semantics.
  5. Add pre-validation gate for STIX bundle ingestion — raw JSON object-count cap and nesting-depth cap before passing to stix2 library.
  6. Define AggregatedRisk behavior when all providers fail — explicit sentinel state, not an absent record.
  7. Split AttackPath aggregate — summary state on root, steps as a lazily-loaded child collection.
  8. Reclassify AttackTechniqueNode and VulnerabilityRecord as reference data entities, not aggregates.
  9. Define domain events for M22 — at minimum: AttackPathComputed, ThreatActorAttributed, IndicatorFused.
  10. Add SSRF mitigation to TAXII endpoint configuration — URL scheme restriction, RFC-1918 DNS block, no-redirect policy — before any TAXII code is written.
  11. Select and document frontend graph visualization library before P5 begins.
  12. Define PathStatus state machine with transition rules.
Final Verdict

This architecture is NOT ready for M22 implementation without structural redesign.

The strategic direction is correct and the domain foundation (M18 threat intel, M21 investigation engine, PostgreSQL security graph) is production-grade. However, there are 8 P0 critical issues — primarily the unresolved dual-graph model, the undefined global vs. tenant table architecture, the SSRF vector in TAXII configuration, and the STIX parsing memory risk — that represent structural defects which will either: (a) produce incorrect implementation if decided ad-hoc during coding, or (b) require migration rollbacks to fix after the fact. Resolving the 12 required pre-implementation decisions listed above and running the BFS performance proof-of-concept should take approximately 2–3 days of design work. After those decisions are documented and approved, M22 implementation can begin with high confidence.
