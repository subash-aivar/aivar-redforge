03

Gap Analysis

Already Implemented

The threat_intel bounded context from M18 delivers a solid foundation: per-org provider configuration, TTL-cached enrichment storage, eight real provider adapters, IOC correlation trigger, provider health monitoring, geolocation, ASN, and IP reputation. Tenant isolation is enforced at the database FK level. The evidence domain model, security graph, and investigation engine are all production-grade and ready to integrate with.

Partially Implemented

  • Domain/URL/hash IOC types — schema and adapters exist; correlation chain is IP-centric; domain/URL/hash paths are under-tested and not surfaced in the main enrichment flow.
  • Cross-provider confidence aggregation — each provider's score is stored in its raw semantics (AbuseIPDB 0–100 confidence, GreyNoise noise/riot booleans, Spamhaus DROP list membership). No application-layer aggregation model exists to produce a unified, explainable risk signal from multiple sources.
  • Investigation source integration — M21's source_adapters.py defines the interface; threat_intel is not registered as a correlation source.
  • Frontend threat intel panel — indicator list, enrichment drill-down, and provider health exist in the UI; there is no attack surface intelligence view, no MITRE technique mapping, no threat actor profile, no attack path visualization.

Missing (M22 must build)

  • MITRE ATT&CK domain model (Techniques, Tactics, Groups, Software) with local caching from the public ATT&CK STIX bundle
  • CVE/NVD feed integration with EPSS scoring and CISA KEV overlay
  • Threat actor profile aggregates
  • STIX 2.1 ingestion pipeline (structured threat intelligence objects)
  • Attack path engine — evidence-backed, graph-traversal-based, no fabricated paths
  • Cross-provider confidence aggregation with source weighting and conflict resolution
  • Background synchronization workers (MITRE ATT&CK, CISA KEV, Spamhaus, Abuse.ch are all static feeds that can be bulk-cached)
  • Threat intel knowledge graph projector (wire threat_intel entities into the security graph)
  • Threat intel → investigation correlation source adapter
  • Frontend: attack path visualization, MITRE heatmap, threat actor profile, CVE panel

Deferred / Not Applicable

  • VirusTotal — commercial API, non-trivial per-query cost. Deferred until commercial tier is established. Provider slot reserved.
  • MISP compatibility — MISP is a self-hosted platform. M22 will define a STIX-based ingestion interface that MISP exports can be imported through; native MISP API protocol is deferred.
  • OpenCTI compatibility — same pattern: OpenCTI exports STIX 2.1; the STIX ingestion pipeline covers the import path. Native OpenCTI API integration is deferred.
  • TAXII server (hosting) — RedForge as a TAXII consumer is in scope. RedForge as a TAXII server (publishing) is out of scope for M22.
  • ATT&CK Navigator compatibility — the Navigator-compatible JSON export format is achievable as a small export endpoint once the ATT&CK domain model exists; included in M22 as a late-phase deliverable.

Proposed Bounded Context

Design principle: M22 extends the existing threat_intel bounded context rather than creating a parallel one. A new attack_path context handles attack path aggregates, which are composite read models backed by the security graph and threat intelligence — not raw event sources.

Aggregates

AggregateContextDescription
ThreatIndicatorthreat_intelAlready exists. Gains MITRE ATT&CK technique associations and CVE linkage. Existing threat_intel_indicators table extended.
ThreatActorProfilethreat_intelNew. Canonical threat actor identity with aliases, attributed techniques (ATT&CK), attributed campaigns, and confidence. Built from STIX threat-actor and intrusion-set objects.
AttackTechniqueNodethreat_intelNew. Canonical MITRE ATT&CK technique (T-number, name, tactic, sub-technique parent). Read-only — loaded from the ATT&CK STIX bundle; never mutated by users.
VulnerabilityRecordthreat_intelNew. CVE + CVSS + EPSS score + CISA KEV flag. Keyed by CVE ID. Updated from NVD + EPSS API + CISA KEV list.
AttackPathattack_pathNew. An evidence-backed traversal: ordered list of AttackStep value objects, each tied to a technique, an observed/inferred flag, confidence, and evidence provenance. Tenant-scoped. No fabricated steps.

Value Objects

  • TechniqueId — validated ATT&CK T-number (e.g. T1190, T1190.001)
  • TacticId — ATT&CK tactic (e.g. TA0001)
  • CveId — validated CVE-YYYY-NNNNN format
  • EpssScore — 0.0–1.0 probability, with percentile and model date
  • AggregatedRisk — cross-provider confidence with per-source breakdown: never a scalar from nowhere
  • StixObjectRef — STIX 2.1 object ID (UUIDv4 with type prefix)
  • AttackStep — (technique, entity, observed|inferred, confidence, evidence_ids, timestamp)
  • PathConfidence — path-level confidence derived from the weakest link in the step chain
  • FusionWeight — per-source trust weight used in aggregation, admin-configurable

Repositories

  • ThreatActorRepository — by org, by STIX ID, by attributed technique
  • AttackTechniqueRepository — by ID, by tactic, full-text search by name
  • VulnerabilityRepository — by CVE ID, by EPSS threshold, by KEV flag
  • AttackPathRepository — by org, by entity ID, by root technique, by confidence floor
  • Extends existing ThreatIntelIndicatorRepository with technique/CVE join queries

Services

  • AttackTechniqueSyncService — downloads + parses the ATT&CK STIX bundle; idempotent upsert
  • VulnerabilitySyncService — NVD API, EPSS API, CISA KEV list; incremental by modified date
  • StixIngestionService — accepts a STIX 2.1 bundle (from TAXII pull, file upload, or clipboard); maps to domain objects; validates provenance
  • ThreatFusionService — cross-provider aggregation with configurable source weights; produces AggregatedRisk
  • AttackPathService — builds evidence-backed paths using security graph traversal + threat intel correlation
  • ThreatIntelInvestigationAdapter — registers threat intel as a source domain for M21 CorrelationEngine
  • ThreatIntelKnowledgeProjector — writes threat_intel entities into the security graph as typed nodes

Policies

  • IndicatorTTLPolicy — expiry rules per provider and indicator type; dynamic refresh on hit-before-expiry
  • FusionConflictPolicy — when two providers produce contradictory verdicts, higher-weight provider wins; tie breaks by recency; conflict recorded in AggregatedRisk
  • InferenceGatePolicy — an attack step may only be marked inferred if at least one adjacent step is observed and confidence ≥ MEDIUM
  • PathExplosionPolicy — max depth and max branching factor; caps graph traversal to prevent explosion on large graphs

Background Workers

  • AttackTechniqueSyncWorker — weekly; MITRE ATT&CK STIX bundle (public, no API key)
  • VulnerabilitySyncWorker — daily; NVD modified feed + EPSS + CISA KEV
  • IndicatorRefreshWorker — on-demand + scheduled re-enrichment of aging indicators for active investigations
  • ThreatIntelProjectionWorker — event-driven; writes new threat actors, techniques to the knowledge graph

Attack Path Engine

Hard invariant: No attack step is ever fabricated. Every step in a path must be traceable to: (a) an observed event in the RedForge telemetry pipeline, or (b) a confirmed IOC match, or (c) a security graph edge whose source evidence is recorded. Inferred steps are allowed only when gated by InferenceGatePolicy.

Evidence Sources for Path Construction

SourceStep typeHow it enters the graph
Suricata/Zeek alertObservedTelemetry ingestion → security graph edge (existing flow)
DDoS detection (M19)Observedddos_incidents → security graph node + edge
Behavioral anomaly (M20)Observedbehavioral_detections → security graph node + edge
IOC match (threat_intel)Observedthreat_intel_enrichments with IOC_MATCH kind → graph edge
MITRE ATT&CK technique relationshipInferredATT&CK relationships table: "uses", "subtechnique-of", "mitigates" — provides the inferred step if adjacent observed step exists
Threat actor attributionInferredThreatActorProfile → attributed techniques; if an observed technique matches a known actor, subsequent actor-attributed techniques become candidate inferred steps

Path Model

AttackPath:
  id: str (ULID)
  organization_id: str
  root_entity_id: str       # entity where the path begins
  terminal_entity_id: str   # entity where path terminates (or None if ongoing)
  steps: list[AttackStep]
  path_confidence: PathConfidence   # weakest-link of step confidences
  technique_coverage: list[TechniqueId]  # deduplicated
  attributed_actors: list[str]          # threat actor IDs if attribution exists
  first_step_at: datetime
  last_step_at: datetime
  status: PathStatus  # ACTIVE | CONTAINED | HISTORICAL
  evidence_count: int

AttackStep:
  sequence: int
  technique_id: TechniqueId | None   # mapped ATT&CK technique (if known)
  entity_id: str                     # the entity involved at this step
  step_type: StepType                # OBSERVED | INFERRED
  confidence: CorrelationConfidence  # reuses M21 enum (LOW/MEDIUM/HIGH/DEFINITIVE)
  evidence_ids: list[str]            # FK to domain/evidence/ records
  source_domain: SourceDomain        # DDOS | BEHAVIOR | THREAT_INTEL | TELEMETRY
  observed_at: datetime | None
  inferred_from_step: int | None     # sequence of the observed step that gates this

Traversal Algorithm

BFS from a seed entity (typically an IP flagged as an IOC, or an entity involved in a behavioral detection). At each hop:

  1. Query security graph for all edges from the current entity within a configurable time window.
  2. For each edge, determine if it maps to an ATT&CK technique via the technique registry.
  3. Apply InferenceGatePolicy: a hop may be INFERRED only if the incoming edge is OBSERVED and confidence ≥ MEDIUM.
  4. Apply PathExplosionPolicy: max depth 12 hops, max fan-out 8 per node.
  5. Record the step with full evidence provenance.
  6. Continue BFS until no new nodes qualify or policy caps are hit.

Risks

Scalability

ATT&CK STIX bundle size The Enterprise ATT&CK STIX bundle currently contains ~700 techniques, ~14 tactics, ~140 groups, and thousands of relationships. An upsert-on-load strategy without batching will lock the attack_techniques table. Mitigation: batch upsert in transactions of 100; run sync worker at low-traffic hours.
Graph explosion in attack path BFS A dense security graph (large tenant, months of telemetry) can produce exponential fanout. Mitigation: PathExplosionPolicy hard caps (depth 12, fan-out 8) with early termination; precompute paths for active investigations rather than on-demand for all entities.

Race Conditions

Duplicate STIX ingestion Two concurrent TAXII pulls or two workers running the ATT&CK sync simultaneously will attempt upserts on the same STIX IDs. Mitigation: stix_ingestion_log table with a per-(org, source, stix_id) unique index; upsert with ON CONFLICT DO NOTHING; stix_ingestion_log acts as the idempotency gate.
Enrichment race on indicator upsert Two concurrent enrichment requests for the same (org, type, indicator) triple will race to insert threat_intel_indicators. Existing ux_tii_org_type_indicator unique constraint handles this; the upsert must use ON CONFLICT DO NOTHING RETURNING id and then query for the existing id. This pattern needs to be explicitly verified in the enrichment service before M22.

Cross-Tenant Risks

Shared intelligence bleed MITRE ATT&CK and CISA KEV are global (not per-tenant). They must be stored as global read-only tables, never in a tenant-scoped table. Attack paths and threat actor attributions that reference these must enforce organization_id isolation at the path/attribution layer, not the technique layer. The technique table must never carry an organization_id column.
Indicator enrichment data bleed Already mitigated by FK isolation in migration 0029. M22 must audit that new fusion tables follow the same pattern.

False Correlations

Threat actor attribution over-confidence A single IOC match to an actor's known infrastructure is weak attribution evidence. The domain must never produce an ATTRIBUTED_TO edge with confidence above MEDIUM unless multiple independent evidence sources corroborate it. The FusionConflictPolicy must include a minimum corroboration count for actor attribution.
Path narrative pollution If inferred steps are allowed too liberally, a path can chain speculative hops into a compelling but false attack narrative. The InferenceGatePolicy must be rigorously tested with adversarial cases where no adjacent observed step exists.

Provider Outages

NVD API instability NVD has a history of API availability issues and rate limit changes. Mitigation: bulk download with incremental sync; cache CVE records locally; circuit breaker on the NVD adapter; operator alert when last successful sync is >48h old.

Cache Poisoning

Stale cached enrichment used as current evidence An enrichment cached 90 days ago is returned as current reputation evidence in an active investigation. Mitigation: expires_at is already in the schema; the enrichment service must refuse to return expired records as evidence in investigation correlation (it may serve them in the UI with a staleness warning). M22 must add a freshness check to ThreatIntelInvestigationAdapter.
10

Recommendation

Proceed with M22 in seven phases as described. The existing threat_intel bounded context from M18 provides a production-grade foundation that M22 extends rather than replaces. The security graph, evidence model, and investigation engine from M19–M21 are all ready to integrate with.

Prioritized Implementation Order

  1. P1 first — ATT&CK + CVE/KEV foundation requires no API keys and no new infrastructure. It unblocks all subsequent phases. Tests are straightforward (static data, idempotent upserts).
  2. P2 before P3 — STIX ingestion enables threat actor profiles, which the fusion layer needs for attribution confidence rules.
  3. P3 and P4 in parallel — fusion layer and security graph integration are independent; they only join in P5.
  4. P5 (attack path) is the M22 proof milestone — it is the highest-value deliverable and the one most likely to surface unexpected graph shape issues. Do not defer it to the end.
  5. P6 before P7 — background workers need to be operational before the frontend can show meaningful live data.

What M22 Will Not Do

  • No fabricated attack paths or AI-generated threat narratives
